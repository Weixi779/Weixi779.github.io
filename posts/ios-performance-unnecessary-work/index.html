记录一次列表的性能优化

从 Instruments 的调用栈回到代码，找出真正值得优化的东西

近期有一个长列表的重构需求。图文列表已经按新的结构重写了一遍，滚动起来却总觉得还差一点。里面有图片，有长短不一的标题，有横向切换的小卡片，也有一些文字模糊和淡入淡出的效果。单独看都不复杂，放在一起，偶尔还是会觉得顿一下。

很自然地开始猜测：是不是嵌套列表太多？是不是自适应高度不合适？是不是承载页面的框架需要换一种设计？

不过，有的时候想太多没用，还是得实际测一下。于是打开 Instruments，开始录制。最后落到代码上的改动，比最初猜想的小得多，就把这次定位和优化的过程记录下来。

文中的业务名称与代码已做泛化. 数据来自同一台真机的五轮录制, 使用优化构建与 Animation Hitches 模板. 操作和录制长度没有严格对齐, 用来定位与复测, 不计算整体提升百分比. 表中的采样权重都是整段录制的累计值, 并非单次调用耗时.

录制与复测

为了看看卡顿时到底在做什么, 用 Instruments 录了一段 Trace. 之后一边检查调用栈, 一边调整代码, 再重新录制, 前后留下了五份记录.

几轮录制的整体效果对比放在文末. 下面先记录几处具体问题, 以及对应的修改.

第一处: 高频路径里的对象复用

整段录制里谁排第一, 还不能直接回答滚动为什么卡. 先把范围收回卡顿附近, 看主线程当时在忙什么, 再顺着调用栈回到代码.

第一处追到了标题的模糊效果. 把相关调用展开, 可以收成下面这条链:

配置标题 Cell
  └─ 生成标题图片
      ├─ 把文字绘制成图片
      └─ 模糊处理
          ├─ 创建 CIContext
          ├─ 配置高斯模糊滤镜
          └─ 输出图片

单看这条链, 每一步都有用途. 回到配置代码才看到问题: 同一个标题再次出现时, 这些准备工作也会再走一遍.

这里的 CIContext 每次都会新建. 它背后有渲染资源的初始化, 也维护着已编译 kernel 等缓存, 适合重复使用. 修改很直接, 把它保留下来, 后续处理使用同一个上下文:

private static let context = CIContext(options: nil)

Apple 的文档也建议复用上下文. static let 是一种持有方式, 由渲染器持有同样可以, 关键是避免在高频路径里反复初始化.

接着复用生成的图片

上下文留下来了, 但每次配置标题, 仍然会重新截图、计算模糊. 同样的标题滚出屏幕再滚回来, 输入没有变化, 生成的图片也可以继续用.

于是, 继续把图片从 Cell 的生命周期里拿出来:

  • 标题图片由当前标题集合持有, 滚出屏幕的 Cell 不再把它一起带走.
  • 标题内容、文字属性或显示倍率改变时, 重新生成; 不再使用的标题从集合里移除.
  • 清晰与模糊之间的切换, 继续由 View 完成动画.

下面是泛化后的缓存判断. 这里比较富文本内容和倍率, 是为了避免“文字字符串相同, 但颜色已经变化”时误用旧图.

@MainActor
final class TitleImageStore {
    private struct Entry {
        let text: NSAttributedString
        let scale: CGFloat
        let image: UIImage
    }

    private static let context = CIContext(options: nil)
    private var images: [String: Entry] = [:]

    func image(
        for text: NSAttributedString,
        scale: CGFloat,
        makeImage: () -> UIImage
    ) -> UIImage {
        if let cached = images[text.string],
           cached.text.isEqual(to: text),
           cached.scale == scale {
            return cached.image
        }

        let image = blur(makeImage(), using: Self.context)
        images[text.string] = Entry(
            text: NSAttributedString(attributedString: text),
            scale: scale,
            image: image
        )
        return image
    }
}

blur 在这里省略了原有滤镜细节; 实际修改保留了模糊半径、边缘扩展、裁剪和输出倍率, 也对照了不同倍率下的新旧输出. 调用方仍需要在主题变化时重新提供正确的文字属性. 缓存不会自动知道外界发生了什么.

第二轮录制里, 目标路径的变化很明显:

主线程累计采样权重初始录制标题资源复用后
标题模糊组件相关调用栈241ms31ms
其中包含 CIContext 初始化的采样143ms4ms
录制长度41.1s42.1s

这一轮同时复用了上下文和标题图片, 两层重复工作一起减少了. 表里的 CIContext 是标题路径的子集, 不能相加, 也不能把全部变化都归到那一行 static 上.

其他高频路径也可以这样检查

这里前后处理了两层重复工作: 先复用处理图片的上下文, 再缓存相同输入生成的图片. 顺着对象创建这一层看, 常见的例子还有:

  • DateFormatter、NumberFormatter: 相同用途、相同配置的格式器可以复用, 避免逐项创建, 也别为了共享一个对象而反复切换配置. 使用新的 FormatStyle 时, Foundation 已经会缓存相同样式, 通常不需要再手动维护静态 formatter. Apple 文档
  • NSRegularExpression: 固定 pattern 可以编译一次、重复匹配; 这个对象不可变, 也支持跨线程匹配. Apple 文档

这类修改往往没有几行代码. 值得留意的是: 对象背后的准备成本有多大, 它又在这条路径里被创建了多少次? 配置稳定、创建频繁时, 复用才更可能带来明显收益.

第二处: 连接手表后才遇到的卡顿

这一处发现得挺巧. 当时我戴着 Apple Watch, 手机会给手表同步图片, 这才触发了平时不容易注意到的一条路径. 展开调用栈后发现, 图片缩放、编码和文件写入都在主线程上执行, 和页面加载、滚动争夺时间.

顺着图片同步的调用往下看, 取图虽然是异步的, 完成回调里的加工却还在主线程上. 把队列标出来, 改动就很直观了:

调整前
主线程: 取图完成 → 缩图 → 编码 → 写文件 → 提交传输

调整后
主线程: 取图完成
          ↓
后台:   缩图 → 编码 → 写文件
                         ↓
主线程:              检查请求是否仍有效 → 提交传输

异步取图只说明图片晚一点回来, 后面的代码在哪个线程执行, 仍然得沿着回调看.

修复本身很直接: 把图片加工和文件写入移到后台, 完成后回到主线程确认请求仍然有效, 再提交传输. 同时把重复请求的检查提前, 避免同一需求反复加工.

图片同步路径累计采样权重调整前调整后
主线程140ms未采到
后台线程6ms150ms
录制长度41.0s44.1s

这组数值里, 工作只是换了位置. 没有什么神奇的 API 把缩图、编码和写文件优化掉, 后台仍然要做这些事. 复测时, 对应路径的采样从主线程转到了后台, 不再和滚动抢同一段时间, 体感也顺了一些. 表里的“未采到”按字面理解就好, 不代表绝对零成本.

回头想想, 如果那次没有连接手表, 这份 Trace 很可能根本不会出现这段开销, 也就顺着漏过去了. 性能录制能看到什么, 也取决于当时实际触发了哪些使用场景.

第三处: 少做一次, 也是一种优化

继续往下看, 调用栈里还有 Cell 的配置和复用清理. 这些名字太熟了, 很容易直接略过. 但展开里面做的事, 又能看到一些没必要的往返: 刚拆掉就重建, 刚清空就赋值. 这一轮改的都是这些小地方.

图片数量没变, 就继续用

一组图片叠层在 reset 时会把数量设为零, 移除所有 ImageView. 下一次配置, 又创建视图、加入 StackView、安装约束. 前后即使都是两张图, 也完整拆建了一次.

调整后保留已有的图片槽位, 不足时创建, 多余时清理并隐藏, 下次需要再拿回来用. 旧图片请求仍然要取消, 隐藏的槽位也不能继续占据排列宽度.

马上要覆盖的内容, 不必先清空

标题先设为空、统计数字先归零, 紧接着又被新内容覆盖. 这个中间状态没有展示给用户, 却已经触发了文字和布局更新.

代码上的调整, 就是从 prepareForReuse() 里删掉这些清空操作. 下面保留当时的改动形式, 控件名称做了简化:

 override func prepareForReuse() {
     // 原有的请求、订阅和回调清理仍然保留
-    titleView.configure(title: nil)
-    subtitleLabel.attributedText = nil
-    subtitleLabel.isHidden = true
-    sourceLabel.text = nil
-    statsView.configure(playCount: 0, commentCount: 0)
 }

下一次配置本来就会设置标题、说明文字和统计数字, 因此不需要先赋一个空值或零, 再马上赋新值. 对于可选内容, 配置时也要直接覆盖, 不能只在有值时才更新:

// 每次配置都赋值：没有副标题时，nil 也会覆盖旧文字
subtitleLabel.attributedText = content.subtitle
subtitleLabel.isHidden = content.subtitle == nil

这样, 静态内容直接从旧值更新到新值, 复用时仍然清理旧请求、订阅和回调. 内容和显示环境都没变时, 也可以跳过重复生成和赋值; 主题变化时仍然要刷新.

前提是下一次配置必须完整. 有副标题到没有副标题、有图标到没有图标, 都要明确设置文字和显隐, 不能依赖 reset 帮忙擦掉上一条内容. 验证时也要让同一个 Cell 连续切换这些状态.

确定要展示, 再创建

还有一处更小的调整: 图标先创建出来, 最后才判断是否插入标题. 把判断提前, 不展示时就不用创建了.

// 原来
let icon = makeBadge()
let title = makeTitle(icon: showsBadge ? icon : nil)

// 修改后
let icon = showsBadge ? makeBadge() : nil
let title = makeTitle(icon: icon)

这些修改放在一起, 复测时对应路径的采样也减少了:

prepareForReuse 调用栈226ms103ms
render 调用栈271ms198ms
录制长度44.1s35.6s

改动没有多少代码. 只是调用一个 API 之前, 多想一步它会触发什么, 这一次有没有必要.

优化之后, 也要知道什么时候停

做到这里, 主要的收益已经拿到了. 前面几条路径少做了重复工作, 图片加工也离开了主线程, 滚动体验达到了这次可以接受的程度.

后面还看过一些标题测量和布局细节, 也做了少量简化, 但没有再看到前面几处那样明显的收益. 那就先停在这里. 热点列表里总会有排在前面的调用, 不必为了让数字更好看, 把剩下的代码也重写一遍.
