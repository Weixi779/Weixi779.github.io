只是想暂存一段 JSON

从一个分页游标出发，重新检查 JSON 的相等与数字边界，留下了自己的思考

现在项目里的分页游标由服务端生成。上一次接口返回什么，客户端就暂存什么，下次请求还回去。里面有啥内容，移动端毫不关心。

古早的项目用 ObjectMapper，这个游标直接用 Any 记录。作为一个习惯了现代 Swift 的开发者，Any 会直接污染整个数据模型的类型设计，导致一堆系统协议无法使用。我希望游标能跟着模型一起遵循 Codable，也能直接比较两个 Pager 是否相同。

之前调研过解析库，从 Property Wrapper 到 Swift 宏，各式各样带着 AnyCodable 腔调的东西都用过。本以为这应该算不上什么新问题。把 JSON 的几种合法值收进枚举，再补上几个协议，大概就够了。

后来发现，真正麻烦的东西，全藏在这个“大概”里。

从 0/1 开始

最初让 AI 去找参考，拿回来的还是那几个熟悉的名字。尤其是那个生产力不足的年代，基本上是把一段代码拷过去能跑就行，所以市面上的大部分实现都大同小异。

Foundation 桥接以后，NSNumber(value: 1) 可以通过 as? Bool 得到 true。如果一个包装类型先尝试 Bool，再尝试数字，收到的 1 就可能被编码成 true，0 则变成 false。

其他问题也陆续出现。有的实现把无法解码的数字退成 null；有的在嵌套解码失败后，只留下一个顶层错误；还有的把模型的蛇形键转换应用到了动态对象内部，让 some_key 和 someKey 撞到了一起。

这样实现是否可行？逻辑上是可行的，但我本次的目的是尽可能地保证存储的东西“不变味”，暂存一个 JSON 值，需要检查的远远不只是“它有没有遵循 Codable”。

然后，第一个讨论停在了 number 上。

Decimal 看起来已经够了

JSON 只有 number，到了 Swift，却要决定它落在 Int、UInt64、Double，还是 Decimal 里。

最直观的写法是挨个尝试。先读整数，失败了再读浮点数。可这个顺序并不像看起来那么可靠：在本机 Foundation 的探针里，1.0000000000000001 请求解码为整数，得到的就是 1。后面的分支不会再执行，因为前面已经“成功”了。

统一用 Double 更省事，但普通的 64 位 ID 就可能受影响：

‹/›Text
9007199254740992
9007199254740993

两个相邻整数进入 Double 以后，可能变成同一个值。拿来展示也许不容易发现，拿来比较 Pager，就已经改变了结果。

于是试了一轮 Decimal。Int64、UInt64 的边界，普通小数，以及生成的两万个整数、两千个有限范围小数，都表现不错。1、1.0、1e0 也能够按同一个数值比较。看起来问题已经收得很小。

但继续验证，又出现了一些不太直观的结果。

直接写 Decimal(19.99) 时，传入的其实是 Double 类型的浮点字面量，在进入 Decimal 之前精度就已经失真了（必须写成 Decimal(string: “19.99”) 才能保持干净）。超长小数则可能在解码时被舍入，之后再怎么往返，测试依然是绿的。第一次解码已经舍入了，后面再怎么往返，也只能证明这个舍入后的值很稳定。

可我最初只是想把它存起来，并不打算拿游标里的数字做任何数学运算，更不准备手写一个任意精度的计算库。

既然不计算，为什么不能存 String

我不期望自己写出来的东西完美无瑕，只期望它能解决 99% 的日常问题；但若真遇到那 1% 的极端情况，也不至于完全束手无策。

后来灵光一闪：既然如此，数字在内存里依然是数值，但能不能额外保留一份原始文本？业务需要用时，如果明确知道类型就自己去转；转不出来也没关系，退回默认值即可。

于是想看看别的强类型语言是怎么设计的，去找了一些参考。

Go 标准库的 json.Number 做法就很直接：

Go
type Number string

String() 读取文本，Int64() 和 Float64() 按需转换。开启 Decoder.UseNumber() 后，动态值里的数字便可以走这条路径。

我曾短暂倾向过按文本比较，让 1 和 1.0 不相等，毕竟写法确实不同。

但最直接的一堵墙，还是 Foundation 的接口。

Swift
let text = try container.decode(String.self)

这句话要求当前位置本来就是 JSON string。它并不会把没有引号的 1.2300 作为原文交出来。先读 Decimal，再取 description，通常已经变成了 1.23；如果前面发生过舍入，有效数字也回不来了。

反过来，编码一个 String，输出自然带引号。给 JSONNumber 实现 Codable，也不会因此多出一个直接写入原始数字 token 的标准容器接口。

尝试保留信息

讨论到这里，一条看似完整的方案出现了：自己解析 JSON，保存数字文本，再实现 Decoder 的容器，让业务模型继续遵循 Codable。

能做，但有点重了。为了一个基础类型，再维护一套模型解码能力，已经偏离最初想要的规模。我还是希望尽量复用系统原生的 Codable 机制，于是接下来的方案，主要围绕着如何在原生体系下做扩展展开。

这里正好可以利用两个现成的机制：userInfo 和 codingPath。解码容器虽然不直接公开数字原文，但 userInfo 允许从入口携带额外的上下文；而在嵌套解码每一个字段时，codingPath 又清楚地记录了当前所在的层级路径。

当然，这条路必须从原始 Data 开始。若上游已经通过 ObjectMapper 或 JSONSerialization 转成 Any，之前没留下的信息，后面不会自己长回来。

哦，我亲爱的 AI

验证没问题了，想着是结束了。但是最近 Astra 降智得厉害，我还是有点不太放心，于是就问了一嘴：咱们这写法性能咋样？

给了一个 benchmark，一份约 1.1 MB、带少量游标数字的分页响应，普通解码约 7.5 ms，加上扫描后接近 29 ms。看完直接无语了，原来它最初的实现，是每碰到一个数字，就从根节点全量做一次深度遍历 / 全局文本扫描…..基础设施就写出来这个水平，最近它的表现让我不放心是对的。问了问有没有什么优化想法，大概最后定的是这个版本。

只索引目标路径经过的容器，无关的值快速跳过，同一层的索引缓存下来，供后续数字复用。找到 score，需要经过根对象、分页对象和游标对象，不需要再为 items 里的每条记录建立第二棵树。

正式实现的 release 构建，结果收到了这个范围：

分页响应 普通解码 保留数字原文 额外耗时
约 22 KB 0.174 ms 0.199 ms 0.024 ms
约 220 KB 1.627 ms 1.759 ms 0.132 ms
约 1.1 MB 7.993 ms 8.770 ms 0.778 ms

最后一点小问题

有一个边缘的例子是：

JSON
{"some_key": 1, "someKey": 2}

模型开启蛇形键转换后，属性 someKey 和字典原本的键 “someKey” 可能会产生相同的 codingPath，从而命中错误的字段。我们可以接受“可能拿不到原始文本”，但绝对无法接受“理直气壮地拿了一个错的数”。

原文保留下来了，但默认比较和编码仍然使用存储的数值。需要原始精度时，要显式读取 originalText；它还不能保证把收到的数字原样交回去。

所以 originalText 最后仍然是可选值。能可靠定位就保存，存在歧义或输入形式暂不支持，就退回普通数值解码。这个 Optional 是实验留下的边界。

最终留下的，是系统 Codable、明确的值比较，以及一条可选的数字原文通道。没有高精度运算，也没有自己的 Encoder。最初那句“给我什么就还回什么”，其实也没有完整实现，到这里已经不能不加说明地继续使用了。实际规则与限制

还是决定留下来

其实这篇文章最难抉择的，不是所谓技术方案上的取舍，而是我在想要不要把这篇留下来。此前有段时间，疯狂地产出这种「小短文」，让我自己的文章有了所谓「CSDN」的风味，加之最近写的文章太重了，字数重、情感重、逻辑重，这种「小短文」放进「重力场」会直接被引力撕碎。

但其实是我多虑了。这背后不仅有具体的考量与取舍，而且只有真正动笔去写，思考才会有痕迹。如果不写这篇小短文，我甚至想不起来早在 2024 年写《浅谈 Swift 模型解析》时，就已经留过一节“关于 Any”。当时只停留在 JSONSerialization 和 AnyCodable；两年后再回到同一个十字路口，挖掘得更深了，也形成了只属于自己的权衡。工程代码最终呈现的，往往只有被选中的那唯一一条路；而写文章，就是把那些未被选中的风景与思索记录下来——即使若干年后回看，可能会觉得它无比稚嫩。
