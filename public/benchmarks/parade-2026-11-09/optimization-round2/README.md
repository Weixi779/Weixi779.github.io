# 第二轮临时优化：快速路径、LIS、原生后台与 ListKit

2026-11-09。Parade 基线 `dedfb5907f54890b3e0b11da99610e933cea5508`；ListKit 使用 Iron-Ham/Lists 的 `221e1513f2786a4e5e836c9b76092c3bd6e61575`。所有改动留在临时实验，生产源码、默认 DataSource 和文章均未修改。

## 候选与边界

| 候选 | 变化 |
| --- | --- |
| 原实现 | 现有 StagedCollectionDataSource＋SectionedDiff，额外加入各版本一致的计时与 UIKit 操作计数。 |
| 上一版后台规划 | 上一轮 worker：主线程投影身份与内容，后台 Diff、结构计划和校验，再回主线程提交。每次都进入后台。 |
| 快速路径＋按规模调度 | 基于上一版。对身份序列未变的 Section，跳过该节结构匹配但保留内容变化；没有结构操作时跳过中间快照及其索引构造。无动画且无结构批次时直接更新内容与布局。总量小于 1,000 时同步计算，达到 1,000 时后台计算。仍是原贪心移动策略。 |
| 再加 LIS | 在上述快速路径上，使用 LIS 选择 Section 和每个 Section 内无需显式移动的存活项；跨组移动继续保留。 |
| 原生主线程 | 生产 DiffableCollectionDataSource 适配。 |
| 原生后台 | 从同一适配复制，Presenter、内容比较、身份 token 和 Cell 注册保持相同；原生 apply／初始 reload completion 入口始终由同一后台串行队列调用，等待完成后返回。 |
| ListKit | 原始六个 ListKit Swift 源文件单独编译，没有改算法和调度。外面使用与系统适配对应的 Parade 快照、内容比较、token、Cell 注册和布局处理。实际精确更新传 animatingDifferences: true，应用全局关闭 UIView 动画。 |

快速路径版本把 Section 跳过、无结构规划短路、直接内容更新和 1,000 项调度阈值组合起来；它们的各自收益没有在本轮继续拆分。LIS 版本相对快速路径版只有移动选择的差异。1,000 是本次采用的对照阈值，不是对真实业务调优后的推荐值。

完整 worker 沿用上一轮的临时边界：为了复用现有规划与校验，在后台创建局部 Presenter 计算快照，再将结果还原为实际展示引用。无结构快速路径省去了这一步，但有结构变化时仍保留这些转换和类型擦除。没有把整个规划器重写成纯整数内核；剩余差距不能直接当作这一架构的性能上限。

新增 LIS 仅用于内置默认算法的临时计算路径；公开 SectionedDiff 的既有接口和直接调用行为、任意自定义算法协议均保持原状。自定义算法仍走既有校验路径。

## 同一套场景与计时

100／1,000／10,000 项，九种场景，三轮独立进程。四个实验版本在每个规模和轮次交错顺序；每个进程均同时测自身 staged、原生主线程、原生后台和 ListKit，候选顺序在样本间打乱。每组预热 3 次、正式 10 次，共 36 个正式进程、12,960 个正式 UI 样本。另有不计入统计的六个功能冒烟进程。

使用同一台 iPhone 18 Pro／iOS 27.0 模拟器、M4 Max 宿主机、Xcode 27.1。固定 320×480 视口、36 高 label Cell、FlowLayout，关闭动画和预取。每个样本先初始化 host、完成初始布局、flush 并等待 30 ms，随后才开始计时。

总耗时包含捕获目标 Presenter、注册准备、内容比较、该后端所需的 snapshot／plan 构建、apply 等待，以及最后 layoutIfNeeded。所有候选统一校验 Section／Item 身份与数量、可见 Cell 的 ID 和 revision。所有正式样本的 reloadData 计数必须为零。

host 使用真实的 ViewRegistry、CollectionViewBridge、CollectionViews 与 DataSource；不包含业务 SectionController 的状态捕获、Orchestrator 外层排队等待或业务交互回调。ListKit 自身的 Task 串行链属于其 apply 实现，仍计入耗时。

这是固定无动画场景下的完整更新延迟，不是显示帧时间。直接 reconfigure 与 batch completion 本来就有不同完成机制；本实验统一等待各 API 返回，再同步完成布局并验证可见内容。它不证明动画中间帧、滚动中的不卡顿或复杂自适应布局表现。

计时 harness 沿用 Swift 5 language mode、-O、whole-module-optimization。Parade 源文件与 harness 同模块，ListKit 是独立静态模块；模块边界也是这个接入方式的一部分，不能把耗时差全部归到算法。另以真实 Swift 6 Package 配置验证两种新的 Parade 实现。原始 JSON 里的历史 cpuWarmups／cpuRuns 字段没有执行对应 CPU lane，本轮只统计 records 中的 UI 样本。

## 原生后台与 SDK 注解

原生后台候选使用 completion 入口，调用处断言非主线程，完成处断言主线程。初始化与正式更新都使用同一个串行队列；每次等待完成，不与下一次更新重叠。共享 Presenter 和视图仍留在 MainActor。正式样本全部通过这些断言与结果检查。

当前 SDK 的该入口仍标记 @MainActor @preconcurrency。此前以及本轮前复核的 Swift 6 独立探针有隔离警告但运行成功。计时 harness 的 Swift 5 配置不会把这一矛盾消除；这个后台候选只是对运行时能力与性能的实验，不是已解决 SDK 契约的生产方案。

## 校验保留与测试调整

实际输入仍由原有 CollectionSnapshot 校验。结构有变化时，原有操作冲突检查、中间快照唯一性、批次重放和最终身份验证仍保留。没有结构变化时不构造空的结构计划；这一短路只用于内置、已匹配的计算结果，不用于信任任意自定义算法。

两种新实现各运行 159 项测试、14 个 suite：原有 157 项加两项实验校验。实验校验穷举 0…7 项共 5,914 个排列，并运行 200 组包含跨组迁移、Section 增删和内容变化的固定随机输入。每个优化结果都另外交给完整计划验证器重放；LIS 对小排列使用独立二次复杂度 oracle 检查最少移动数。

159 项测试针对两种新的 Parade 实现及测试中原有的系统适配。新增原生后台和 ListKit 适配器的验证范围是本轮九种性能场景及对应身份／内容／操作检查，没有声称它们通过了全部业务生命周期测试。

临时测试中有三处有意调整：两处原来要求内容／补充视图更新必须提交一次批次，改为快速路径的零次；LIS 版本另将左旋的贪心三次移动预期改为一次。其他内容、交互、自适应高度、Cell 替换、生命周期与 FIFO 断言均保留。早期仅因这些操作次数预期而失败的日志也保留在复现包中，不能描述成“原有测试一字不改全部通过”。

没有验证真机性能、峰值内存、首页完整业务、持续滚动和所有系统版本；没有把实验阈值、无动画完成方式或算法选择写进默认实现。
